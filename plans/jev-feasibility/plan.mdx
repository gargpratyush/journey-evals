# Jev Eval: feasibility first, framework second

**Objective:** demonstrate the complete loop on owned test software: **run a user journey, discover a useful defect, preserve evidence, give the report to a coding agent, repair the application, and rerun unchanged checks**. Then establish enough reliability, economic value, and transfer to a second application to justify extracting a reusable framework.

**Current status, 18 September 2026: implementation exists; CP0 through CP4 are GREEN and CP5 is AMBER, all on measured source revisions.** The fixed three-run clean cohort verified 3/3 bookings with no abandoned browser stalls, and CP3's live trio was revalidated on the current runtime without rescoring the exposed holdout. CP4 closed the defect-to-repair loop on two separately constructed defects, each injected as a real application-source edit and repaired on the first of two permitted attempts by a coding agent that was never told what had been injected. The intermittent Chrome stall that previously blocked CP2 was diagnosed to Chrome itself and is now bounded and recorded rather than hidden. **CP5 ran all four arms and did not clear the bar**: held-out quality and collector overhead are GREEN, but the cost advantage is 7.27x against a declared 10x gate, and 7 of 60 live journeys were reported passing while the browser actor had silently abandoned the journey. The demonstrated advantage is latency, 14.0x, not cost and not quality. CP6-7 have not run; CP6's text-entry credential is resolved by reusing the `gpt-5.6-luna` deployment and now needs only a second application. The campaign uses a cumulative USD 0.40 Jev estimate cap, raised from USD 0.10 on the owner's explicit authorisation, and has spent about USD 0.060 of it. The larger proposed budgets below remain unapproved.

This is the execution plan to follow before the broader [architecture roadmap](..\jev-eval\plan.html). Its checkpoints take precedence over that roadmap's initial phase ordering: a thin repair loop and second-application transfer happen **before framework extraction**, not after building all five evaluator families.

**Yes, we are using `jev-ultrafast` as the execution runtime.** The initial spike imported the unchanged reference clone. The approved implementation seeded `jev-test` from the pinned source using WSL Git and now extends its loop, browser adapter, snapshots, and model transport. `jev-eval` is installed from this owned fork, not the neighboring reference checkout. Section 13 specifies when, where, and how each upstream component participates.

## 1. What we are trying to prove

A useful first demonstration is a synthetic flight-booking app. A user searches, selects a fare, chooses a test passenger, and completes a sandbox booking. The booking succeeds, but the fare increases silently during checkout. The runner identifies the measured price change, distinguishes a legitimate disclosure from an unexplained change, and supplies the relevant before/after evidence.

A coding agent receives that report, fixes the actual application, and reruns the same journey. The clean app is no longer flagged. Restoring the original defect makes it detectable again. A happy-path booking test alone would not have asserted the quality of the disclosure.

**This is a controlled experiment, not a promise to notice every detail of arbitrary applications.** Jev is text-only. The initial evidence is DOM state, events, timing, and screenshots for human inspection. Actual screenshot interpretation requires a separate vision model and is not silently included.

<Callout id="experiment-decision" tone="decision">
Build the smallest working loop first. Use three checks, one local app, one owned browser, and local artifacts. Do not start with a plugin API, generic journey language, dashboard, automatic repair service, or all five evaluator families. Start framework design only after the explicit admission gate in Checkpoint 7.
</Callout>

| Hypothesis | What would support it | What would falsify or narrow it |
| --- | --- | --- |
| H1: the execution plumbing works | An isolated browser reaches declared states; a separate verifier confirms the result; failures never become success. | Unsupported controls, event loss, duplicate mutations, or unreliable reachability dominate the run. |
| H2: the observations are sufficient | Relevant facts and transition timing survive into the report, including partial-evidence markers. | The evaluator needs information the observation builder never captured. |
| H3: Jev adds useful judgment | It detects a semantic defect and rejects legitimate lookalikes, beyond the frozen deterministic baseline. | It mostly repeats exact rules, misses the target defects, or flags normal behavior. |
| H4: the report enables repair | An agent repairs the application from the report, without weakening tests or evaluator policy. | Reports need undocumented explanation, hallucinate evidence, or lead to unrelated repairs. |
| H5: the economics are worthwhile | Matched-quality comparisons show a meaningful cost advantage within an acceptable run time. | Retries, helper calls, uncertainty, or vision costs remove the advantage. |
| H6: the core transfers | A second app works with journey/test-data bindings rather than rewritten evaluator logic. | Everything depends on flight-specific prompts, labels, or state extraction. |

## 2. Checkpoint map and the meaning of green

| Checkpoint | Primary question | Exit evidence | What it permits |
| --- | --- | --- | --- |
| 0. Access and boundaries | Can we run safely with bounded cost and known capabilities? | Redacted preflight manifest and one small synthetic API smoke. | Local implementation experiments. |
| 1. Instrumented browser | Can we observe and verify without model dependence? | Offline/browser contracts, complete or explicitly partial telemetry, isolated cleanup. | Testing the actor against the fixture. |
| 2. Autonomous clean journey | Can the actor complete the intended task? | Three fresh clean runs and independent booking checks. | Adding one useful defect detector. |
| 3. Evidence-backed detection | Does the evaluator distinguish defects from legitimate behavior? | Blind positive/negative examples, matching evidence, initial holdout results. | Attempting the repair loop. |
| 4. Report-driven repair | Does the entire code-test-fix-retest loop work? | Two repair demonstrations with unchanged oracles and restored-defect checks. | Claiming a narrow end-to-end demonstration. |
| 5. Repeatability and economics | Is the loop useful beyond a selected successful run? | Frozen holdout, live repeat matrix, cost/latency ablation, retained failures. | A credible single-app feasibility claim. |
| 6. Second-app transfer | Is there a reusable core, including normal text entry? | A frozen-core pilot on a different app with measured results. | A framework-design review. |
| 7. Framework admission | Is a reusable framework now justified? | All required gates, evidence manifest, explicit limitations, extraction proposal. | Designing and implementing the small shared framework. |

**GREEN:** the predeclared required checks pass and their artifacts exist. This authorizes the next experiment, not production deployment. **AMBER:** a useful partial result, missing capability, unrun comparison, inconclusive evidence, or a failed quantitative gate. Fix or narrow the claim; do not silently promote it. **RED:** invalid experiment, safety/data failure, systematically unusable quality, or no useful semantic contribution.

Each checkpoint ends with one short receipt: verdict, exact versions, runs/cases attempted, passed/failed/unknown counts, actual and estimated cost, artifact locations, unresolved limitations, and the next permitted action. A missing result is `NOT RUN`, not green.

After a failed checkpoint, allow one bounded corrective iteration with a specific hypothesis and new evidence. If the same gate still fails, pause expansion and record a pivot decision. Do not rerun until lucky, change thresholds after seeing holdout results, or discard provider/browser failures.

For Checkpoints 3, 5, and 6, any scored results used to change extraction, prompts, models, thresholds, retries, or execution policy retire that scoring set from admission use. Keep it for diagnosis/regression; freeze the revised candidate and use a fresh, equivalently constructed holdout or live matrix for the affected gate. Repeating an exposed set is not new admission evidence.

## 4. Checkpoint 1 - browser and evidence without AI

Before judging Jev, prove that the system can measure the facts it will send. Reuse `Browser`, `snapshot.js`, `browser_operation`, and the local checks in `scripts\check_guards.py`.

Launch an owned Chrome for Testing process with a fresh non-default profile and loopback endpoint. Configure the pinned harness explicitly before imports. Run only the synthetic app; never attach to a normal signed-in browser. If the pinned transport cannot meet isolation and event requirements after one bounded spike, use Playwright for that transport instead of inventing a CDP library. Record the change and rerun this checkpoint.

The preliminary run proved the explicit `BU_CDP_URL` path with installed Chrome and a dedicated `BU_NAME`/harness home; it did not pin Chrome for Testing or prove profile separation across runs. Add a regression for **initial capture -> inference-length pause -> native action -> post-action capture**, retaining timeouts. Test any proposed activation, timeout, or browser-version change before calling the screenshot issue fixed. Do not silently drop required evidence or retry the already executed action when capture fails.

Create the smallest fixture: search, a flight choice, a test-passenger choice, checkout, confirmation, and a resettable fake booking store. Keep the independent booking verifier outside the actor's observation. A script may drive this checkpoint through trusted observed controls; label it **scripted instrumentation validation**, not autonomous capability.

Implement only the first needed evidence:

- Immutable before/action/after states with step and document IDs.
- Action attempt and execution acknowledgement, with no mutation retries after uncertain execution.
- Selected fare and checkout total with currency/fare identity; exact arithmetic in code.
- Input, loading-feedback, and results timestamps; relevant console/network failures.
- Initial, failure, and final screenshots as local evidence, not Jev input.
- Versioned JSON result, an append-only event journal, and a fresh independent booking verification.

Install collection before navigation. Use one owner for the harness's draining event queue. Export document-scoped events and sequence watermarks through a runtime binding; represent a navigation tail without an acknowledged closing boundary as partial. Never infer absence of feedback across a partial window.

**Required checks:** isolated profiles do not share fixture state; a normal booking creates exactly one matching record; a wrong route/date or missing record fails independently; stale targets do not execute; an ambiguous mutation stops; executed actions survive failed observations; missing mandatory evidence cannot pass; cancellation closes owned resources; secrets do not appear in artifacts.

Exercise immediate navigation during a simulated slow inference interval. The required result is either retained evidence or an explicit gap, not an impossible promise of perfect unload delivery. Also capture a brief loading indicator that starts and ends between endpoint snapshots; this tests the continuous collector rather than just the final DOM.

**Gate:** every required invariant passes without a paid model call. These are correctness conditions, not percentage targets. Retain the journal and verifier output so the next checkpoint is testing the actor, not hidden plumbing.

**Defer:** full motion profiling, pixel diffs, all-element overlap scans, HTML polish, and generalized observation adapters.

**Effort guide:** 1-2 days, with a shorter timebox for transport selection.

## 6. Checkpoint 3 - one useful semantic finding, then three checks

Start with **fare-change disclosure**. Code establishes that the selected and checkout fares increased on the same basis. Jev judges only whether the observed message explains the change and clearly asks for acknowledgement. Render a report from evidence and templates; do not ask Jev to generate arbitrary bug descriptions or source locations.

For increased-fare legitimate cases, independently verify an actual acknowledgement after the relevant disclosure and before booking. A message asking for acknowledgement is not proof that acknowledgement occurred. Keep that event/order check separate from Jev's interpretation of the message; missing required evidence means `UNKNOWN`.

Create paired cases:

| Case | Correct behavior |
| --- | --- |
| Same fare throughout | No price-change finding. |
| Increased fare with no explanation | Evidence-backed candidate defect. |
| Increased fare clearly disclosed and acknowledged | No unexplained-change finding. |
| Increased fare disclosed, but booking proceeds without the required acknowledgement | Not a legitimate control: record the independent acknowledgement-check failure, or `UNKNOWN` if its required evidence is missing. |
| Different currency, passenger count, tax basis, or ambiguous amount association | `UNKNOWN` or a different explicitly measured fact; do not compare incompatible amounts. |
| Missing/partial disclosure observation window | `UNKNOWN`, not "no disclosure." |
| Page text instructing the evaluator to pass | Treat as untrusted data; cannot alter policy or the independent verifier. |

Then add two adjacent checks using the same pipeline: **interaction effect observed** and **loading feedback during a delayed response**. The latter depends on Checkpoint 1's timeline; it cannot be substantiated with post-action screenshots alone.

Faults are injected through a test-side control channel with opaque run identifiers. Do not expose the active fault in task text, URLs, DOM attributes, model requests, or result IDs available to the evaluator. Keep fixture ground truth and labels separate.

### Small screening corpus

Create 36 independently labeled evidence windows: 12 for each of the three checks, evenly split between real defects and clean/legitimate controls. For each check, reserve six windows for development and six for holdout, keeping near-duplicate scenarios together. That gives a screening holdout of nine positives and nine negatives. Add separate missing-evidence cases; they must abstain and are not counted as ordinary clean negatives.

Freeze extraction, question wording, model ID, and decision thresholds before the holdout. The developer can label fixture cases from their known construction, but the model must not see those labels. If the scored results inform a correction, apply the fresh-holdout rule in Section 2.

**Screening gate:** at least 8/9 held-out defects correctly identified, at most 1/9 false actionable findings on held-out clean controls, at least 8/9 controls receive definitive evaluations supported by complete evidence, and all deliberately missing required-evidence cases abstain. A finding counts only if its category, subject, and evidence match the labeled defect. Unknowns are not correct negatives; report them in the original attempted-case denominators. This tiny gate screens obvious failure; it does not calibrate production confidence.

Also run a live clean/broken/disclosed-fare trio and inspect the actual report evidence. All three must produce the expected definitive target evaluations with complete required evidence; `UNKNOWN` does not pass this trio. A frozen-corpus success does not prove the browser reaches or records the right state.

**Important:** semantic findings remain advisory/review-required. Human confirmation of this demonstration's finding permits a repair experiment; it does not promote the general evaluator to a blocking CI rule.

**Receipt:** versioned rubrics, split manifest, confusion counts including unknowns, live trio, and a report with resolvable evidence links.

**Effort guide:** 1-2 days. If the semantic result adds nothing beyond exact rules, stop expanding and revise the product hypothesis.

## 7. Checkpoint 4 - prove the complete repair loop early

Run this before completing the five-family product, a CI integration, or a plugin API.

Use **two separately constructed application defects**, one of which exercises a genuinely semantic judgment such as unexplained fare change. Materialize actual faulty source variants for the repair task; simply switching off a fault-injection flag is not a repair.

For each defect:

1. Freeze and hash the evaluator, journey, independent acceptance checks, and test-side fixture controls. Include a target-specific repair acceptance criterion and its required evidence, covering the user-facing defect rather than booking success alone. Hash non-secret inputs only.
2. Capture a reproducible pre-fix finding with evidence. Review its validity before asking an agent to repair it.
3. Give a coding agent the task, the report, the permitted application source, and evidence. Do not add an undocumented diagnosis or reveal the injected-fault answer.
4. Permit at most two repair attempts. The agent may change application implementation, not the oracle, evaluator, budgets, ground-truth labels, or fault-selection infrastructure.
5. Rerun the unchanged journey and clean/legitimate controls from reset state. Independently check post-fix evidence against the frozen target-specific acceptance criterion; documented human review is sufficient here. Where required, confirm actual acknowledgement after disclosure and before booking.
6. Restore the exact original defect in a separate disposable application copy and show that the unchanged evaluator catches it again.

This can be orchestrated through the current coding-agent session or a small documented invocation. Do not build unattended `--fix`, a vendor-specific multi-agent service, or GitHub integration to prove it. Use a separate worktree/copy where necessary, preserve user changes, and perform Git operations through WSL. No automatic commit/push.

**Gate:** both defects produce valid pre-fix evidence, both are repaired within the bound without changing protected test inputs, both post-fix journeys independently verify, both target-specific repair criteria independently pass, paired legitimate controls receive definitive clean evaluations, and both restored defects reproduce. Save patches and hashes so an external reader can audit the claim.

For the semantic defect, a post-fix report may still honestly say `WARN` for unrelated advisory findings. The gate requires a definitive clean target evaluation plus independent confirmation of the repair, not disappearance of every warning. A target `UNKNOWN`, missing evidence, or mere absence of the original finding never counts as resolution.

**Receipt:** paired before/after/restored run IDs, application patch, protected-input hashes, frozen target-specific acceptance criterion and independent post-fix review, evidence used by the agent, repair attempts, and measured cost/time.

### Implemented result: CP4 GREEN, 2/2 targets

The application under test was first separated from the harness so a defect could be a real source edit rather than a runtime flag. `jev_ultrafast/app/booking.html` and `jev_ultrafast/app/pricing.py` are now the entire application; the oracle, evaluators, journey and fixture controls live outside it and are hashed before the repair task is handed over. `repair-prepare` copies that source into `artifacts\feasibility\repair\<target>-<case-id>\app`, edits it, keeps the byte-identical injected copy as `as-injected`, and writes `freeze.json`.

| Target | Injected source defect | Pre-fix finding | Repair the agent made | Verification |
| --- | --- | --- | --- | --- |
| `fare-surcharge` (semantic) | an undisclosed peak surcharge added in `pricing.py` | `fare` defect, confidence 0.99 | deleted the surcharge so checkout charges the selected fare | post-fix clean; disclosed-and-acknowledged control clean at confidence 1.0; restored defect caught again at 0.99 |
| `silent-confirmation` (user-facing) | `booking.html` built the confirmation markup but never rendered it | `effect` defect, confidence 0.95 | rendered the confirmation after the booking succeeds | post-fix clean at 0.97; pristine control clean; restored defect caught again at 0.95 |

Both defects were chosen so the booking itself still succeeded: the independent verifier **passed before the repair in both cases**, and the actor reported `done` in both cases. Only the evaluator caught the user-facing problem, which is exactly the "covering the user-facing defect rather than booking success alone" requirement.

Establishing "the declared response deadline elapsed" required a real measurement rather than an assumption, so the journey now takes one deliberate settle observation 1200 ms after the last action; the confirm-to-evidence interval was 103 ms before that change, which cannot distinguish a missing effect from a pending one.

Each repair was performed by a coding sub-agent in its own context, given only the brief, the journey evidence and the two application files, and told not to read the harness. It was never told which fault was injected; both diagnosed it correctly and unaided. Both passed on the **first** of the two permitted attempts. After each repair, `repair-verify` reconfirmed that every protected input hash and the whole source fingerprint were unchanged, that only application files differed, and stored the unified diff.

CP4 used **63 Jev requests, 96,048 accounted tokens, about USD 0.004** at the documented rate, and 28.5 s of total inference latency across 8 live journeys. Cumulative campaign spend is about **USD 0.021** of the USD 0.10 cap.

**Limits.** This is two defects in one small synthetic application, both repaired on the first attempt. It demonstrates that the loop closes; it is not evidence of repair reliability, of difficulty coverage, or of behaviour on defects whose repair is ambiguous. The instruction not to read the harness was not technically enforced, only instructed and then checked by hashes after the fact.

**What we can now say:** a narrow end-to-end code-test-fix-retest loop has been demonstrated, on two defects in one synthetic application. We still cannot claim a generally reliable framework.

**Effort guide:** 0.5-1.5 days after detection works.

## 8. Checkpoint 5 - repeatability, false positives, and economics

No public 10x claim or framework investment based on a selected video. Freeze the candidate and run two complementary evaluations.

### A. Frozen observation holdout

Build a **new holdout of 90 labeled evidence windows**: 30 per check, including 15 defects and 15 clean/legitimate cases per check. Do not reuse Checkpoint 3's development or exposed holdout cases. Vary copy, component layout, legitimate feedback, and relevant amounts/timing. Add at least 12 missing/partial-evidence cases outside the 90. Once these results inform candidate changes, retire this set and score a fresh holdout under Section 2's rule.

**Provisional investment gates:** at least 12/15 true defects detected per check; at most two false actionable findings across the 45 controls and at most one per check; at least 90% precision among actionable semantic findings; at least 80% decision coverage on complete-evidence cases, including at least 12/15 definitive control evaluations per check; all deliberately missing required-evidence cases abstain.

Report every denominator. Unknowns on known positive cases count as missed detections; unknowns on negatives are reported as abstentions, not correct negatives. Coverage and recall prevent a model that abstains on everything from looking accurate.

These are project investment thresholds, not claims that model confidence values are calibrated to them.

### B. Live runs

Run **60 planned journeys**: ten fault-injected and ten paired clean/legitimate runs for each of the three checks. Randomize their order, reset browser/backend state, vary predeclared fixture inputs and timing, and retain every attempt.

**Gate:** at least 27/30 clean journeys independently complete; at least 8/10 target defects detected per check; at most two clean runs out of 30 receive a spurious actionable finding, with at most one in each ten-run control group; at least 8/10 planned controls per check receive definitive target evaluations supported by complete evidence; and no false `PASS` where a declared acceptance condition actually failed.

Failure to reach a defect is a missed end-to-end detection plus an execution/coverage failure, not a removed sample. Browser/provider outages remain visible. Control unknowns and execution failures remain in the ten-attempt control denominators, not counted as correct negatives. Record complete results separately from the all-attempt rates so reliability and evaluator quality are not conflated.

### C. Matched baselines and cost accounting

Use the same frozen evidence and held-out labels for:

| Arm | Purpose |
| --- | --- |
| Frozen deterministic checks alone | Show what requires no model. |
| The same checks plus Jev | Measure incremental semantic value and total overhead. |
| The same checks plus one conventional structured-output text LLM | Compare equivalent semantic work at measured quality and coverage. Requires its own authorized provider access. |

Before scoring, predeclare a representative, cost-conscious conventional text model from the authorized providers and document the selection rationale. Choose its model version, prompt, batching, and retry policy using development cases only; freeze both arms before opening the scoring holdout. Do not choose an expensive comparator after seeing the results. A changed arm requires fresh admission data under Section 2's rule.

Batch the conventional LLM's questions fairly; do not compare one Jev batch against deliberately unbatched LLM calls. Use each provider's supported request shape and record its actual version, token usage, retries, and pricing. Do not compare text-only Jev against a vision model performing extra work.

**Semantic value gate:** at least one useful semantic defect category meets the quality gates and detects held-out cases the frozen exact-rule baseline does not, without exceeding the false-alarm budget. This demonstrates practical value for these rubrics, not an assertion that no deterministic program could ever implement them.

**Economic gate for the Jev-centered framework:** target at least **10x lower semantic-inference cost per correctly resolved complete-evidence case** than the matched text-LLM baseline, with precision and recall no more than five percentage points worse and decision coverage no more than five points lower. Both arms must meet the quality floor. Show raw cost, correctly resolved count, false findings, and abstentions beside the ratio. Attribute the measured advantage to this named comparator/version and workload, not to conventional LLMs in general.

If the comparator cannot meet the quality floor, the 10x comparison is inconclusive rather than a Jev victory. If no baseline credential is available, mark economics `NOT RUN`; do not replace measured comparison with advertised token-price ratios.

Also report total journey cost including actor, helper, retries, repair calls, and browser time. A 10x improvement in the inexpensive evaluator alone is not a 10x reduction in the complete development loop.

### D. Latency and collector overhead

Provisional target for this small fixture: at least 95% of planned live journeys terminate with a persisted result within a 90-second run budget; failures remain failures even if they terminate quickly. Track provider/runner errors, not just elapsed time.

For collector overhead, run ten matched scripted pairs with instrumentation off/on in randomized order, without model calls. Report native interaction times and collector CPU/elapsed work. Investigate a median slowdown greater than 10% or 20 ms per scripted step, whichever tolerance is larger. This is a diagnostic gate on this fixture, not a browser-wide performance guarantee.

For evaluation overhead, report the added model/capture wall time separately; if median overhead exceeds 25% of the actor-only journey, try batched next-decision evaluation only after validating equivalence. Freeze the revised loop, retain exposed cases as regressions, and score affected admission comparisons on fresh cases under Section 2's rule.

**Checkpoint gate:** quality and live-repeatability requirements pass; the semantic contribution is demonstrable; economics are measured; latency fits the declared budget. Below-10x but otherwise useful results are AMBER and require an explicit investment/pivot decision, not automatic framework admission.

**Effort guide:** 1-3 days for cases, runs, and analysis, excluding open-ended prompt tuning.

### Measured result: CP5 AMBER

## 11. What "sure enough" does and does not mean

| Evidence achieved | Defensible conclusion | Still not established |
| --- | --- | --- |
| Checkpoint 2 | One supported autonomous happy path works. | Useful bug discovery or general reliability. |
| Checkpoint 4 | The narrow evaluation-report-repair-rerun loop works. | Stable precision, savings, or portability. |
| Checkpoints 5-6 | The tested checks have measured quality/economics and transfer to a second app. | Arbitrary applications, arbitrary visuals, or production merge gating. |
| Checkpoint 7 | A small reusable framework is a justified engineering investment. | Comprehensive QA coverage or a guaranteed business. |

Thirty clean runs without a false alarm still do not prove a tiny false-positive rate. Under an independence assumption, the rough "rule of three" upper 95% bound after zero observed events is about `3 / n`; even 100 independent clean cases only suggests a bound around 3%. Repeated states from one app are correlated, so apparent sample size can overstate confidence.

After framework extraction, blocking CI requires a separate programme: diverse application holdouts, human-reviewed labels, version-specific calibration, shadow runs, drift monitoring, and a product-owner-approved false-positive/false-negative tradeoff. Semantic checks remain advisory until they earn that role.

## 13. Concrete implementation order and reuse

### Runtime decision: use and extend jev-ultrafast

**Use a narrow source fork, not a rewrite and not a permanent black-box wrapper.** `jev-ultrafast` supplies the actor and guarded browser execution; Jev supplies finite decisions; our additions supply continuous evidence, evaluator functions, independent verification, and reports. The external coding agent repairs the target application. These are distinct responsibilities.

There are two deliberately different integration stages:

1. **Completed initial investigation:** imported the unchanged `C:\source\projects\jev-ultrafast` package from a separate environment. External drivers supplied diagnostic fixtures and accounting; they are not the product architecture.
2. **Implemented CP0-3 candidate:** `C:\source\projects\jev-test` is a source fork on branch `feasibility`, based on the pinned commit with remote `upstream`. Existing plans and `.env` were preserved, MIT attribution retained, and no commits or pushes made. The package remains `jev_ultrafast`; the runnable CLI is `jev-eval`. Formal checkpoint execution uses this fork's editable installation.

An outer loop over `Agent.run()` cannot see every failure boundary: a browser action can execute before post-action capture raises, preventing a state from being yielded. The screenshot failures exposed precisely that distinction. Add explicit, small lifecycle recording points inside the fork rather than monkey-patching the live actor or assuming each yield equals one successful action.

Do not start by implementing the entire architecture plan. Keep this first sequence narrow:

| When | Existing code to reuse | How it participates and the smallest new work |
| --- | --- | --- |
| CP0 | `jev_ultrafast\model.py:post_json`, `validate_choice`; pinned dependencies | Use the existing `/v1/systemone` transport, safely map the key name, pin the model, and enforce a combined attempt/cost budget. No SDK rewrite. |
| CP1 | `browser.py:Browser`, `browser_operation`; `snapshot.js`; `scripts\check_guards.py`; `agent.py` recording boundaries | In the owned fork, preserve node identity, freshness/hit tests, and single-consumption actions. Add browser/profile ownership, pre-navigation telemetry, immutable observations, separate evaluation projection, capture-failure regression, fake store, and independent verifier. |
| CP2 | `agent.py:Agent.command` and `run`; `model.py:choose`/`action_space`; `questions.py:NEXT_ACTION`/`TARGET` | This remains the actual actor: Jev chooses operation and compatible target heads, and code executes only that selected operation. Wire the instrumented runner and independent final outcome; do not replace the policy with a flight-specific script. |
| CP3 | `model.py:post_json` and `validate_choice`, plus the new observation hooks | Add three plain QA functions/rubrics and a separate evaluation request. Navigation `DONE` does not become an evaluator verdict. Render measured facts and finite findings into evidence-backed JSON/HTML. |
| CP4 | The same forked runner, evaluator, and report | Hand the report to the existing coding-agent session. Repair target-app source only; freeze runner/evaluator/oracle inputs. No new agent orchestrator and no Jev-generated patches. |
| CP5 | The same runner and persisted observations | Replay frozen evaluation inputs; compare deterministic, Jev, and predeclared text-LLM arms. Measure actual actor/helper/evaluator calls separately. No second runtime for benchmarks. |

**Not reused as production architecture:** the inspector's singleton state, Google-specific verifier, recorder script as a library, or the action snapshot as a complete UX/accessibility tree. The upstream UI can remain a debugging aid. A Playwright transport is a contingency only if the scoped harness/isolation/event spike fails; it is not a second backend to build in parallel, and changing transport need not discard Jev's finite-choice policy.

Use the existing offline tests and browser guard checks. Add a compact parametrized test module for verdict aggregation, evidence gaps, result-basis references, request budgets, and no duplicate actions. Test code paths without paid APIs; live evaluations are explicit experiments, not ordinary unit tests.

**Planning ranges:** access/instrumentation and the first autonomous journey usually consume the first 2-4 engineering days; a real report-driven repair demonstration is a reasonable first-week target; repeated quality/economic work and a second pilot may take another week or more. These are allocations to test assumptions, not delivery guarantees. Stop conditions and evidence gates override the calendar.
